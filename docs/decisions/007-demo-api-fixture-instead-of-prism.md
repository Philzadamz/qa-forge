# 007 — `infra/demo-api` (FastAPI) instead of Prism for the API-runner test fixture

**Status:** accepted · **Date:** 2026-10-01

## Context
PRD §13.6 calls for "a mock API (Prism from an OpenAPI file) for API runner tests." Prism
(`@stoplight/prism-cli`) mocks an API purely from a static OpenAPI spec — no real server logic
behind it, just schema-shaped example responses.

## Decision
Built `infra/demo-api/` instead: a small real FastAPI app (a "petty cash transfers" resource —
Bearer auth, a transfer limit, idempotent-by-reference creates, owner-scoped reads) whose
`/openapi.json` is itself the spec the "OpenAPI spec source: URL" runner input parses. This
app is both the spec source and the live target in tests — one process, not a spec file plus a
separate mock process to keep in sync.

Reasons over Prism:
- **No new runtime dependency.** This is otherwise an all-Python test suite (`pytest`,
  `httpx`, `playwright`'s Python bindings); Prism is a separate Node CLI process the test
  suite would need to spawn, health-check, and tear down — another case of exactly the
  process-management code `tests/execution/conftest.py` already has for
  `infra/demo-target`/`infra/demo-api`, just for a tool with no other role in this codebase.
- **A static-spec mock can't exercise real behavior.** PRD's own category list for generated
  API cases includes idempotency, permission/IDOR, and auth-missing/invalid/expired — none of
  these are meaningfully testable against a mock that returns canned examples with no actual
  state or logic. `infra/demo-api` genuinely enforces its limit, its ownership check, and its
  idempotent-replay behavior, so a generated case for any of those categories exercises real
  behavior, not a fixture that would pass regardless of what the runner actually sent.
- **One source of truth.** A hand-maintained OpenAPI YAML file drifts from Prism's mock
  behavior over time with no compiler to catch it. `infra/demo-api`'s spec is generated by
  FastAPI from the same Pydantic models that define its actual behavior — they cannot drift
  apart.

## Consequences
- `infra/demo-api` is deliberately small (three routes) — it's a test fixture, not a reference
  implementation of "a good API" beyond what's needed to exercise the PRD's test categories.
- The real Prism-based flow (arbitrary spec file in, mock server out, no app code needed) is
  still what a user would reach for to mock *their own* third-party API when that's all they
  have — `api_spec.py`'s OpenAPI parser works identically against a spec served by a real app
  or a Prism mock; nothing in the runner assumes `infra/demo-api` specifically. Only the test
  suite's fixture choice is affected by this decision, not the product's spec-parsing code.
- If a future phase needs to test against a spec with no real backend (e.g. validating the
  parser against a large third-party spec with hundreds of endpoints `infra/demo-api` has no
  reason to implement), introducing Prism (or a lighter static-mock library) for that specific
  case remains straightforward — this decision doesn't preclude it, it just means the
  everyday API-runner tests don't need it.
